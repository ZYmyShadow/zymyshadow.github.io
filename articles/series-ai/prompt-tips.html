Prompt Engineering 实用技巧整理

Prompt 技巧 实战 更新于 2026-07-20 · 宗主

提示
概要：本文系统整理提示词工程（Prompt Engineering）的核心技巧，涵盖角色设定、Few-shot 示例、思维链（CoT）、输出格式控制、上下文管理等实用方法。每个技巧均附带实际案例与效果对比，帮助读者快速掌握与大模型高效沟通的方法论。文中案例基于 GPT-4o、Claude 3.5、Qwen2.5 等主流模型的实际测试，效果可能因模型而异。

什么是提示词工程

提示词工程（Prompt Engineering）是通过精心设计和优化输入给大语言模型的文本指令，来引导模型产生更准确、更有用、更符合预期输出的技术。它不涉及修改模型参数或训练数据，而是通过改变「提问方式」来释放模型的全部潜力。

提示词工程的核心价值在于：同一个模型，好的提示词和差的提示词之间，输出质量可能有天壤之别。根据 Anthropic 和 OpenAI 的官方文档，以及多个独立评测（如 Chatbot Arena 的提示词优化实验），经过优化的提示词可以将模型在特定任务上的准确率提升 20-50%。

本文整理的技巧按照从基础到进阶的顺序排列，每个技巧都可以独立使用，也可以组合叠加以获得更好的效果。

技巧一：角色设定（Role Prompting）

角色设定是让模型扮演特定角色或专家身份，从而引导其以该角色的知识体系、表达风格和专业视角来回答问题。

原理

大语言模型在训练时吸收了海量的多领域文本数据。当指定角色后，模型会激活与该角色相关的知识子集，过滤掉不相关的信息。这类似于人类在「以专家身份思考」时会调用更专业的知识框架。

效果对比

提示词 输出特点 适用场景
无角色："解释什么是 API" 通用百科式回答，覆盖广但深度不足，语言平淡 快速了解概念
教师角色："你是一位有10年经验的计算机科学教授，用通俗易懂的方式向大一新生解释什么是 API" 使用类比（如餐厅菜单）、分步骤讲解、语气亲切，适合初学者 教学、科普
工程师角色："你是一位资深后端工程师，向同事解释 RESTful API 的设计要点" 直接切入技术细节，涉及 HTTP 方法、状态码、版本控制等专业概念 技术讨论、代码审查
产品经理角色："你是一位产品经理，向非技术团队解释 API 的商业价值" 聚焦业务场景、生态系统、合作伙伴集成等商业视角 商业演示、跨部门沟通

角色设定模板

你是一位 [角色/职位]，拥有 [X年] 的 [领域] 经验。
你的专长包括 [技能1]、[技能2]、[技能3]。
你的沟通风格是 [简洁/详细/幽默/正式]。
请用你的专业知识回答以下问题：
[具体问题]
注意事项：角色设定不是万能的。对于需要严格事实准确性的任务（如法律、医疗建议），角色设定可能导致模型「过度自信」地给出不准确信息。此时应在提示词中明确要求「如果不确定，请说明」或「请标注信息来源」。

技巧二：Few-shot 示例

Few-shot（少样本）是在提示词中提供 1-5 个输入-输出示例，让模型通过类比学习来理解任务格式和期望的输出风格。

为什么 Few-shot 有效

大语言模型具有强大的上下文学习能力（In-context Learning）。当看到几个示例后，模型会自动推断出任务的模式、格式要求和风格偏好，而无需额外的指令说明。这在以下场景特别有效：

  • 输出格式有特定要求（如 JSON、特定模板）
  • 需要模型遵循特定的分类标准
  • 输出风格需要与示例保持一致
  • 任务定义模糊，用示例比用文字描述更清晰

效果对比：情感分类

方式 提示词 结果
Zero-shot（无示例） "判断以下评论的情感：'这个手机电池续航太差了，一天要充三次电'" 可能回答"负面"，也可能回答一段分析文字，格式不统一
Few-shot（3个示例） 见下方示例 稳定输出"负面"，格式统一 
# Few-shot 示例提示词
请判断以下用户评论的情感倾向，只回答"正面"、"负面"或"中性"。

示例：
评论："物流很快，包装完好，满意！" → 正面
评论："一般般吧，没什么特别的" → 中性
评论："用了两天就坏了，客服还不理人" → 负面

现在请判断：
评论："这个手机电池续航太差了，一天要充三次电" →

Few-shot 的最佳实践

实践 说明 原因
示例数量 2-5 个 太少学不到模式，太多浪费 token 且可能引入噪声 研究表明 3 个示例通常是性价比最优的
覆盖不同类别 示例应涵盖所有可能的输出类别 避免模型偏向某一类别
格式严格一致 示例的输入输出格式要与实际任务完全一致 模型会严格模仿示例的格式
示例质量优先 选择清晰、无歧义的示例 模糊示例会导致模型输出模糊
排列顺序 将最接近当前任务的示例放在最后 模型对最近的示例关注度更高（近因效应）

技巧三：思维链（Chain-of-Thought, CoT）

思维链（Chain-of-Thought）是提示词工程中最具影响力的技巧之一，由 Google Research 在 2022 年提出。其核心思想是引导模型在给出最终答案之前，先展示推理过程。

CoT 的两种形式

形式 方法 示例
Zero-shot CoT 在问题末尾添加"让我们一步步思考" "这道数学题的答案是什么？让我们一步步思考"
Few-shot CoT 在示例中包含完整的推理步骤 见下方示例

效果对比：数学推理

# 问题：一个商店有 25 个苹果，卖出了 8 个，又进货了 15 个，现在有多少个苹果？

# ❌ 直接回答（Zero-shot，无 CoT）
# 模型可能直接回答 "32" 或 "17"，准确率约 60-70%

# ✅ Zero-shot CoT
# 提示词："一个商店有 25 个苹果，卖出了 8 个，又进货了 15 个，现在有多少个苹果？让我们一步步思考"
# 模型输出：
# "首先，商店原有 25 个苹果。
#  卖出 8 个后，剩余 25 - 8 = 17 个。
#  又进货 15 个，现在有 17 + 15 = 32 个。
#  答案是 32 个苹果。"
# 准确率提升至 85-90%

# ✅ Few-shot CoT（效果最佳）
# 提示词：
# "问题：小明有 10 颗糖，给了小红 3 颗，又买了 5 颗，现在有几颗？
#  思考：原有 10 颗，给出 3 颗后剩 10-3=7 颗，又买 5 颗，7+5=12 颗。答案：12 颗。
#
#  问题：一个商店有 25 个苹果，卖出了 8 个，又进货了 15 个，现在有多少个苹果？
#  思考："

CoT 的适用场景

  • 数学和逻辑推理——效果提升最显著，准确率可提升 20-40%。CoT 让模型将复杂问题分解为简单步骤，避免「跳跃式」错误
  • 代码调试——引导模型逐步分析代码逻辑，定位 bug 原因。比直接问「这段代码有什么问题」效果好得多
  • 复杂决策分析——如方案对比、利弊分析。CoT 让模型展示权衡过程，输出更有说服力
  • 阅读理解——特别是需要从长文本中提取信息并推理的问题
重要发现：根据 Wei et al. (2022) 的原始论文以及后续多项研究，CoT 的效果与模型规模密切相关。CoT 在 100B+ 参数的模型上效果显著，但在小模型（<10B）上可能无效甚至有害。对于 Qwen2.5-7B 这样的小模型，CoT 的提升幅度有限（约 5-10%），而对于 GPT-4 或 Qwen2.5-72B，提升可达 20-40%。如果你的模型较小，优先尝试 Few-shot 而非 CoT。

进阶：CoT 变体

变体 方法 适用场景
Self-Consistency 让模型用 CoT 推理多次，取出现频率最高的答案 数学题、有唯一正确答案的问题
Tree of Thoughts (ToT) 让模型探索多条推理路径，评估每条路径的可行性后选择最优 创意写作、策略规划、多解问题
ReAct 推理（Reasoning）+ 行动（Acting）交替，模型可以调用外部工具 需要实时信息检索的任务（如搜索、计算）
Plan-and-Solve 先让模型制定解题计划，再按计划逐步执行 多步骤复杂任务（如项目规划、数据分析）

技巧四：输出格式控制

输出格式控制是确保模型输出符合程序处理需求的关键技巧。在将模型输出接入自动化工作流时，格式的一致性至关重要。

JSON 格式输出

# 提示词示例
请分析以下用户反馈，并以 JSON 格式输出结果。
要求：
- 包含字段：sentiment（情感）、category（类别）、summary（摘要）、urgency（紧急程度 1-5）
- 只输出 JSON，不要其他文字

用户反馈："我上周下的订单到现在还没收到，客服说已经发货了但物流信息一直没更新，太失望了"

期望输出：
{
  "sentiment": "负面",
  "category": "物流问题",
  "summary": "订单发货后物流信息未更新，客户等待超过一周",
  "urgency": 4
}

结构化列表输出

# 提示词示例
请列出 Python 中列表推导式的 5 个常见用法。
格式要求：
1. 每个用法用 ### 标题
2. 标题下方给出代码示例（用 ```python 包裹）
3. 代码下方用一句话说明适用场景

期望输出格式：
### 1. 过滤元素
```python
evens = [x for x in range(10) if x % 2 == 0]
```
适用于从序列中筛选满足条件的元素。

格式控制的关键指令

指令 作用 示例
"只输出 JSON" 禁止模型添加解释文字 确保输出可直接被 json.loads() 解析
"用 Markdown 表格" 指定表格格式 适合对比类内容
"每个要点不超过 20 字" 控制输出长度 适合摘要、标签生成
"用编号列表" 指定列表类型 适合步骤说明、排名
"不要使用专业术语" 控制语言难度 适合面向普通用户的场景
实用技巧：对于需要程序化解析的输出，建议在提示词中提供完整的输出模板，而不仅仅是描述格式。例如，与其说"输出 JSON 格式"，不如给出一个带占位符的 JSON 模板：{"name": "<姓名>", "age": <年龄>}。这样模型的输出格式会更稳定。

技巧五：上下文管理

上下文管理是指在多轮对话或长文本处理中，有效地组织和管理输入给模型的信息，确保模型关注到最关键的内容。

上下文窗口限制

每个模型都有最大上下文窗口（Context Window），即一次能处理的 token 总数。常见模型的上下文窗口：

模型 上下文窗口 约合汉字数
GPT-4o 128K tokens 约 6-8 万字
Claude 3.5 Sonnet 200K tokens 约 10-12 万字
Qwen2.5-72B 128K tokens 约 6-8 万字
LLaMA 3.1-8B 128K tokens 约 6-8 万字
Gemma 2-9B 8K tokens 约 4000-5000 字

需要注意的是，上下文窗口不等于有效注意力范围。多项研究（如 "Lost in the Middle" 论文）表明，模型对上下文开头和结尾的信息关注度最高，对中间部分的信息容易「遗忘」。因此，关键信息应放在提示词的开头或结尾。

长文本处理策略

策略 方法 适用场景
摘要前置 在长文本前加一段摘要，让模型先了解全局 分析长文档、论文
分块处理 将长文本分成多个块，分别处理后汇总 超出上下文窗口的超长文本
关键信息提取 先用模型提取关键信息，再基于关键信息提问 从大量数据中找特定答案
RAG 检索增强 用向量数据库检索相关片段，只将相关片段放入上下文 知识库问答、文档检索

技巧六：约束与边界设定

约束与边界设定是告诉模型「不要做什么」，防止模型生成不相关内容或越界回答。

常见约束指令

# 知识边界约束
"请只基于我提供的信息回答，不要使用你的训练知识。如果你不知道答案，请说'根据提供的信息无法确定'。"

# 输出长度约束
"请用不超过 100 字回答"
"请列出 3-5 个要点，每个要点一句话"

# 范围约束
"请只讨论技术层面的原因，不涉及商业或政治因素"
"请只针对 Python 3.10+ 回答，不考虑旧版本兼容性"

# 不确定性标注
"如果你对某个信息不确定，请在该信息后标注 [待确认]"
"请区分哪些是事实，哪些是你的推断"

效果对比：约束前后

场景 无约束 有约束
基于文档问答 模型可能混入训练知识，给出文档中不存在的信息 严格基于文档，不知道就说不知道
代码生成 可能使用过时的库或语法 限定语言版本和库版本，输出更可靠
数据分析 可能过度解读数据，给出不确定的结论 区分事实和推断，结论更严谨

技巧七：迭代优化

迭代优化是指通过多轮对话逐步 refine 模型的输出，而非期望一次提示词就得到完美结果。

迭代优化的常用策略

  • 追问细化——"这个方案不错，但请考虑成本因素，给出更经济的替代方案"
  • 指出问题——"第二段的技术描述有误，Redis 不是关系型数据库，请修正"
  • 要求对比——"请同时给出方案 A 和方案 B 的优缺点对比"
  • 指定视角——"请从安全审计的角度重新审视这段代码"
  • 要求自检——"请检查你刚才的回答，有没有事实错误或逻辑漏洞"

自检提示词模板

请对你上面的回答进行自检：
1. 有没有事实性错误？
2. 逻辑是否自洽？
3. 有没有遗漏重要信息？
4. 结论是否有充分依据？

如有问题，请指出并给出修正后的版本。
实用建议：自检（Self-Reflection）是提升模型输出质量的有效手段。根据多项研究，让模型对自己的输出进行审查和修正，可以将准确率提升 10-20%。但需要注意，模型自检并非万能——它可能无法发现自身知识盲区中的错误。对于关键信息，仍建议人工核实。

技巧组合实战案例

实际应用中，多个技巧往往组合使用。以下是一个综合案例：

案例：技术方案评审

# 组合了：角色设定 + Few-shot + CoT + 格式控制 + 约束

你是一位有 15 年经验的技术架构师，擅长分布式系统设计。
请评审以下技术方案，重点关注高可用性、性能瓶颈和安全风险。

评审标准示例：
方案："使用单 MySQL 实例存储用户数据"
评审：
- 高可用性：❌ 单点故障风险，建议主从复制或多活架构
- 性能瓶颈：⚠️ 单机读写有限，用户量超 10 万后可能成为瓶颈
- 安全风险：⚠️ 需确认是否启用 SSL 连接和字段级加密
- 综合评分：4/10
- 改进建议：...

待评审方案：
[粘贴你的技术方案]

请按上述格式输出评审结果。如果方案信息不足，请标注 [信息缺失] 并说明需要补充哪些信息。

提示词设计的原则总结

原则 说明 优先级
明确具体 避免模糊表述，用具体的数字、格式、范围来限定 ★★★★★
提供示例 一个清晰的示例胜过千言万语的描述 ★★★★★
分解任务 复杂任务拆分为多个简单步骤，逐步引导 ★★★★☆
设定边界 明确告诉模型什么该做、什么不该做 ★★★★☆
迭代优化 不要期望一次完美，通过多轮对话逐步改进 ★★★☆☆
适配模型 不同模型对提示词的敏感度不同，需要针对性调整 ★★★☆☆

提示词工程既是一门技术也是一门艺术。以上技巧提供了系统的方法论框架，但最好的提示词往往来自于对具体任务的深入理解和反复试验。建议在实践中建立自己的提示词库，记录哪些技巧对哪些任务最有效，逐步形成个人的提示词工程方法论。

免责声明：本文中的效果对比数据基于 2026 年 7 月的模型版本（GPT-4o-2026-07、Claude 3.5 Sonnet、Qwen2.5 系列），不同版本或不同模型的表現可能有差异。提示词工程的效果受模型版本、温度参数、上下文长度等多种因素影响，文中数据仅供参考。建议在具体使用前针对目标模型进行小规模测试。
